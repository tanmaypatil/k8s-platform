k8s-platform · part 1 of 3

Build Platform Architecture

What actually runs inside the kind cluster when you use tanmaypatil/k8s-platform, which pieces stay up all the time, and which ones are short-lived Jobs that appear for a single build and then go away. Build Jobs are drawn in amber throughout.

The picture in one sentence

One long-running web app (the dashboard) and a stack of Jobs that run to completion: an orchestrator Job per build run, and for each repo a clone Job, a build-agent Job and a build Job. They all share one disk, the workspace PersistentVolumeClaim, and they record progress in one ConfigMap, build-status.

The Kubernetes objects, one by one

Each card names the object as it appears in manifests/base/ or manifests/templates/.

Namespace · 00-namespace.yaml

builds

A folder for objects. Every name below is unique only inside builds, and the RBAC Role only grants rights here.

PVC · 10-pvc.yaml

workspace

A request for 2Gi of disk. kind's default StorageClass hands it to the local-path provisioner, which creates a PersistentVolume (a directory on the node) and binds it. Pods mount the claim, never the PV directly.

ServiceAccount + Role + RoleBinding · 20-rbac.yaml

build-agent

An identity for pods, a list of allowed actions, and the link between them. The orchestrator, build agent and dashboard run as this account so they can create Jobs and patch ConfigMaps in builds, and nothing else.

ConfigMap · 30-config.yaml

platform-config

Settings as key/value pairs: REPOS, GIT_REF, JAVA_8_IMAGE, JAVA_17_IMAGE, AGENT_IMAGE, KEEP_RUNS. Injected into agent pods as environment variables with envFrom.

ConfigMap · 30-config.yaml

build-status

Used as a tiny database. Each key is <build-id>.<repo> and holds a JSON record with the stage, Java version, image and timings. Agents patch it; the dashboard reads it.

CronJob · 40-orchestrator-cronjob.yaml

orchestrator

Suspended, so its schedule never fires. It exists only as a stored Job template: kubectl create job --from=cronjob/orchestrator stamps out a fresh Job from it.

Deployment + Service · 50-dashboard.yaml

dashboard

A Deployment keeps one dashboard pod running and replaces it if it dies. The NodePort Service gives it a fixed port (30080) on the node, which kind maps to localhost:8080.

Job templates · manifests/templates/

clone, build-agent, build

Not applied by up.sh. The agents fill in ${REPO}, ${BUILD_ID} and friends with Python's string.Template and pipe the YAML to kubectl create -f - at run time.

Build Jobs up close

A Job is Kubernetes' object for work that should finish. The Job controller creates a pod, watches it, and marks the Job Complete when the pod exits 0 or Failed when retries run out. Compare that with a Deployment, which restarts its pod forever.

The build Job is the one that does the real work: it runs mvn package in a JDK image the build agent chose for that repo. Here is manifests/templates/build-job.yaml, trimmed, with what each line does.

kind: Job
metadata:
  name: ${JOB_NAME}                       # build-k8s-java17-run-20261101-140500
  labels:
    k8s-platform/stage: build             # lets you query: kubectl get jobs -l k8s-platform/stage=build
    k8s-platform/java: "${JAVA_VERSION}"  # which JDK was chosen, visible with -L
spec:
  backoffLimit: 0                         # a compile error won't fix itself: fail on the first try
  activeDeadlineSeconds: 900              # kill the build after 15 minutes
  ttlSecondsAfterFinished: 3600           # Kubernetes deletes the Job 1h after it ends
  template:
    spec:
      restartPolicy: Never                # Jobs need Never or OnFailure
      automountServiceAccountToken: false # Maven never calls the API, so no credentials in the pod
      containers:
        - name: maven
          image: ${BUILD_IMAGE}           # k8s-platform/java8-maven:dev or java17-maven:dev
          command: ["run-build"]
          env:
            - {name: SRC_DIR,   value: /workspace/runs/${BUILD_ID}/${REPO}}
            - {name: MAVEN_REPO, value: /workspace/m2}     # cache shared across runs
          resources:
            requests: {cpu: 500m, memory: 512Mi}           # scheduler reserves this much
            limits:   {memory: 1Gi}                        # above this the pod is OOM-killed
          volumeMounts:
            - {name: workspace, mountPath: /workspace}
      volumes:
        - name: workspace
          persistentVolumeClaim: {claimName: workspace}

How the JDK is picked. agent/build_agent.py reads pom.xml and checks, in order, maven-compiler-plugin <release>/<target>/<source>, then the properties maven.compiler.release, .target, .source and java.version. k8s-java8 declares maven.compiler.target=1.8, which becomes 8. k8s-java17 declares maven.compiler.release=17. The agent then takes the lowest JAVA_<N>_IMAGE that is at least that version.

The split matters for security. Only the three Python programs need to talk to Kubernetes, so only their pods get the ServiceAccount token. Clone and build pods run code fetched from the internet (git, Maven plugins), and they have no credentials to misuse.

Why one shared PVC works here

The clone Job writes sources, the build Job reads them a minute later in a different pod with a different image. That hand-off only works because both pods mount the same claim. ReadWriteOnce means "one node at a time", not "one pod at a time", and kind has a single node, so every pod can mount it at once. On a multi-node cloud cluster you would switch to a ReadWriteMany StorageClass such as NFS or EFS.

The m2/ folder is why the second run is faster: Maven's downloaded dependencies survive on the PVC between runs, while the pods that downloaded them are long gone.

Try it

kubectl -n builds get pvc,pv
kubectl -n builds get jobs -l k8s-platform/stage=build -L k8s-platform/repo,k8s-platform/java
kubectl -n builds describe job build-k8s-java17-<build-id>
kubectl -n builds exec deploy/dashboard -- ls -R /workspace/artifacts
