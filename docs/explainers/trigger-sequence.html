One Build Run, Traced

Everything that happens after you type ./scripts/trigger.sh: the orchestrator Job is stamped out of a suspended CronJob, then for each repo a clone Job, a build-agent Job and a build Job run one after another, with both repos going at the same time.

The script itself

BUILD_ID="run-$(date -u +%Y%m%d-%H%M%S)"                    # e.g. run-20261101-140500
kubectl -n builds create job --from=cronjob/orchestrator "$BUILD_ID"
kubectl -n builds wait --for=condition=Ready pod -l "batch.kubernetes.io/job-name=$BUILD_ID" --timeout=120s
kubectl -n builds logs -f "job/$BUILD_ID"                  # skipped with --no-follow

Four lines. The script only starts the run and watches it. All the real work happens in pods inside the cluster. The dashboard's Run builds button does the same create job --from call from its own pod.

The sequence

Each pod's arrows really go through the API server (create a Job, patch the ConfigMap, read a Job's status). They are drawn straight to their target to keep the picture readable. Build Jobs are amber.

Step by step

  1. Stamp a Job out of the CronJob

    kubectl create job --from=cronjob/orchestrator run-20261101-140500 reads the suspended CronJob, copies its jobTemplate into a brand-new Job with that name, and submits it. The CronJob never fires on its own; it's just a stored template, which is why the Role grants get on cronjobs.

    The Job controller sees the new Job and creates one pod for it, labelled batch.kubernetes.io/job-name=run-20261101-140500. The pod spec sets BUILD_ID from that label with the downward API (fieldRef: metadata.labels['batch.kubernetes.io/job-name']), so the program learns its own build id without anyone passing it in.

  2. trigger.sh waits, then follows the logs

    kubectl wait --for=condition=Ready pod -l … blocks until the orchestrator pod is running (up to 120s), because kubectl logs fails on a pod that hasn't started. Then logs -f streams the orchestrator's output until the pod exits. That's the [status] … lines you see.

  3. Orchestrator: queue every repo, one thread each

    orchestrator.py parses REPOS from platform-config (name=url,name=url), writes a QUEUED record for each into build-status, and starts a Python thread per repo. From here on the two repos are independent.

  4. Clone Job

    The orchestrator records CLONING, fills manifests/templates/clone-job.yaml with the repo name, URL and build id, and pipes it to kubectl create -f -. The alpine/git pod runs git clone --depth 1 --branch main into /workspace/runs/<build-id>/<repo> on the PVC. With backoffLimit: 2, a failed clone (say, a network blip) gets two more tries in new pods.

    Meanwhile kube.wait_for_job polls kubectl get job -o json every 2 seconds, looking for a Complete or Failed condition. If the clone fails, the repo is marked FAILED with the last log lines as the reason, and that thread stops.

  5. Build-agent Job

    The orchestrator records DETECTING and creates the build-agent Job. This is a second pod running the same agent image, but build_agent.py instead. It opens pom.xml on the PVC: k8s-java8 says maven.compiler.target=1.8, so Java 8; k8s-java17 says maven.compiler.release=17. It picks the lowest JAVA_<N>_IMAGE that's at least that version and records BUILDING with the chosen image.

  6. Build Job

    The build agent renders build-job.yaml with BUILD_IMAGE=k8s-platform/java17-maven:dev (or java8) and creates it. The pod's run-build script prints java -version and mvn -v, runs mvn -B -ntp -Dmaven.repo.local=/workspace/m2 package, tees everything to /workspace/logs/<build-id>/<repo>.log and copies the jar to /workspace/artifacts/<build-id>/<repo>/.

    backoffLimit: 0 means a compile failure fails the Job immediately instead of retrying the same broken code. activeDeadlineSeconds: 900 kills a build that hangs. When the Job finishes, the build agent records SUCCEEDED or FAILED plus buildSeconds and durationSeconds, and exits.

  7. Finish and clean up

    The orchestrator thread sees the build-agent Job finish and reads the final stage. Once both threads are done it prunes: it keeps the newest KEEP_RUNS=10 builds in build-status and deletes older folders under runs/, logs/ and artifacts/ on the PVC. It exits 0 if every repo succeeded, 1 otherwise, which makes the orchestrator Job Complete or Failed. The log stream ends and trigger.sh returns.

    Kubernetes tidies up later on its own: ttlSecondsAfterFinished deletes the clone, build-agent and build Jobs (and their pods) an hour after they finish, and the orchestrator Job after 24 hours. The PVC contents and the status records stay.

The stages a repo moves through

These are the values of stage in each build-status record, which is what the dashboard shows.

A finished record looks like this (from kubectl -n builds get configmap build-status -o yaml, key run-20261101-140500.k8s-java17, fields trimmed):

{"buildId": "run-20261101-140500", "repo": "k8s-java17", "stage": "SUCCEEDED",
 "javaVersion": "17", "image": "k8s-platform/java17-maven:dev",
 "cloneJob": "clone-k8s-java17-run-20261101-140500",
 "agentJob": "build-agent-k8s-java17-run-20261101-140500",
 "buildJob": "build-k8s-java17-run-20261101-140500",
 "cloneSeconds": 4.2, "buildSeconds": 38.7, "durationSeconds": 42.9,
 "message": "Built with Java 17"}

The timings above are an example of the shape, not a measured run.

Watch it happen

Run these in a second terminal while a build is going:

kubectl -n builds get jobs -w -L k8s-platform/stage,k8s-platform/repo,k8s-platform/java
kubectl -n builds get pods -w
kubectl -n builds logs -f job/build-k8s-java17-<build-id>
kubectl -n builds get events --sort-by=.lastTimestamp | tail -20

Experiments worth trying: delete a running build pod and watch backoffLimit: 0 fail the Job instead of making a new pod; set JAVA_17_IMAGE to the java8 image in platform-config and see k8s-java17 fail to compile; add a third repo to REPOS and see a third thread appear.
