What up.sh Builds

A step-by-step trace of scripts/up.sh: how the kind cluster comes up, how the images get inside it, the order in which Kubernetes objects are created, and how the ServiceAccount and RBAC rules decide what the platform's pods are allowed to do.

The whole run as a sequence

Read top to bottom. Solid arrows are commands up.sh sends; dashed arrows are things that happen as a result. The default path (kind, local images) is shown. The registry path is at the end of the page.

Step by step

  1. Create the cluster, or reuse it

    kind get clusters | grep -qx k8s-platform || kind create cluster … makes the script safe to run twice. kind starts one Docker container that runs a full Kubernetes control plane plus a kubelet, so the "cluster" is a single node. cluster/kind-config.yaml adds one port mapping: host port 8080 goes to port 30080 on the node, which is where the dashboard's NodePort Service will listen.

    kind also writes a kubeconfig context named kind-k8s-platform with admin credentials. kubectl config use-context makes every later kubectl call in the script go to this cluster. With CLUSTER_TOOL=minikube the same step runs minikube start --cpus 4 --memory 6g instead.

  2. Build the images and load them into the node

    Three images are built on your Mac's Docker: java8-maven and java17-maven (JDK + Maven + run-build script) and agent (Python + kubectl + the orchestrator, build agent, dashboard and Job templates).

    The node is a separate container with its own image store (containerd), so it cannot see your Mac's Docker images. kind load docker-image copies each one in. Every manifest uses imagePullPolicy: IfNotPresent, so the kubelet uses the loaded copy and never tries to pull k8s-platform/agent:dev from a registry that doesn't exist.

  3. Apply the base manifests

    kubectl apply -k manifests/base runs kustomize, which reads kustomization.yaml, collects the six files and sends the objects to the API server. kustomize sorts objects by kind before sending, so the actual order is the one in the diagram: Namespace first (everything else lives in it), then the ServiceAccount, Role and RoleBinding, ConfigMaps, the Service, the PVC, and the workloads last.

    For each object the API server authenticates you (the admin context from step 1), checks you're authorized, runs admission, and stores it in etcd. apply is declarative: on a second run it compares and only changes what differs.

  4. Controllers bring the objects to life

    Storing a Deployment doesn't start anything by itself. The Deployment controller creates a ReplicaSet, which creates a Pod. The scheduler assigns the pod to the only node. The pod references the workspace claim, and kind's default StorageClass waits for that first consumer before provisioning: the local-path provisioner then creates a PersistentVolume (a directory on the node) and binds the claim to it. The kubelet mounts the volume and the ServiceAccount token and starts server.py.

    The CronJob is stored too, but suspend: true means the CronJob controller never creates a Job from it. Nothing builds until you trigger a run.

  5. Restart and wait for the dashboard

    If you rebuilt the agent image, it still has the same tag (:dev), so the Deployment spec hasn't changed and Kubernetes has no reason to replace the pod. kubectl rollout restart adds a timestamp annotation to the pod template. That changes the template, so the Deployment rolls out a new ReplicaSet and a new pod that runs the freshly loaded image.

    kubectl rollout status blocks until the new pod passes its readiness probe (GET /healthz every 5 seconds), then up.sh prints the URL.

ServiceAccount and RBAC

Your kubectl uses admin credentials. Pods don't get those. A pod runs as a ServiceAccount, and by default that identity can do almost nothing. manifests/base/20-rbac.yaml creates three objects that together give the platform's own pods exactly the rights they need.

What happens on each API call from a pod

Every pod with a ServiceAccount gets a short-lived token mounted at /var/run/secrets/kubernetes.io/serviceaccount/. When agent/kube.py runs kubectl inside the pod, kubectl finds that token automatically and sends it with the request.

Notice what is missing: no secrets, no delete pods, nothing cluster-wide. The clone and build Jobs don't set serviceAccountName, so they run as the namespace's default account, and they also set automountServiceAccountToken: false, so they carry no token at all.

Try it

kubectl -n builds get sa,role,rolebinding
kubectl auth can-i create jobs -n builds --as=system:serviceaccount:builds:build-agent    # yes
kubectl auth can-i delete pods -n builds --as=system:serviceaccount:builds:build-agent    # no
kubectl auth can-i create jobs -n default --as=system:serviceaccount:builds:build-agent  # no
kubectl -n builds get pvc workspace -o jsonpath='{.spec.volumeName}{"\n"}'

The registry path

With REGISTRY=ghcr.io/my-org TAG=1.0.0 ./scripts/up.sh, frame 2 is skipped: nothing is built or loaded. Frame 3 renders manifests/overlays/registry instead of base, swaps REGISTRY_PLACEHOLDER and TAG_PLACEHOLDER with sed, and pipes the result to kubectl apply -f -. The overlay rewrites the image names and adds imagePullSecrets: registry-creds to both the default and build-agent ServiceAccounts, so every pod, including Jobs created later at run time, can pull from a private registry. up.sh then reminds you to create that secret if it's missing.
