k8s-platform · manifest reference

k8s-platform Manifest Guide

Every YAML file in the repo, field by field: what each important attribute does, why it has the value it has, and what changes if you edit it. The YAML shown is the real file with its comments removed; the comments' content is folded into the explanations.

How to read any manifest

apiVersion: batch/v1
kind: Job
metadata:
  name: clone-k8s-java8-run-20261101-140500
  namespace: builds
  labels:
    k8s-platform/stage: clone
spec:
  backoffLimit: 2
  template:            # a whole Pod spec, nested
    spec:
      containers: [...]
status:                # written by Kubernetes, never by you
  succeeded: 1
apiVersion + kind
Which type of object this is. The group in apiVersion (batch, apps, rbac.authorization.k8s.io, or none for core types like Pod and ConfigMap) also appears in RBAC rules. kubectl explain job.spec documents any field.
metadata
Identity: name (unique per kind per namespace), namespace, and labels, the key/value tags that selectors, Services and kubectl -l match on.
spec
The state you want. Controllers keep working until reality matches it. Workloads (Job, CronJob, Deployment) nest a pod template inside their spec.
status
What actually happened, filled in by Kubernetes. You'll see it in kubectl get -o yaml but never in these files.

Four groups, four moments

The files fall into four folders, and each folder is read by a different tool at a different time. Knowing which is the key to the whole repo.

Cluster

Read by the kind CLI once, to create the cluster.

  • kind-config.yaml kind Cluster

Base

Applied by up.sh with kubectl apply -k manifests/base. The platform's permanent objects.

  • 00-namespace.yaml Namespace
  • 10-pvc.yaml PersistentVolumeClaim
  • 20-rbac.yaml ServiceAccount, Role, RoleBinding
  • 30-config.yaml ConfigMap ×2
  • 40-orchestrator-cronjob.yaml CronJob
  • 50-dashboard.yaml Deployment, Service
  • kustomization.yaml Kustomization

Templates

Never applied directly. The agents fill in placeholders and create a Job from each, every run.

  • clone-job.yaml Job (template)
  • build-agent-job.yaml Job (template)
  • build-job.yaml Job (template)

Registry overlay

Used instead of base when you run up.sh with REGISTRY=….

  • kustomization.yaml Kustomization
  • platform-config.yaml ConfigMap patch
  • build-agent-serviceaccount.yaml ServiceAccount patch
  • default-serviceaccount.yaml ServiceAccount

Cluster

Read by the kind CLI once, to create the cluster.

cluster/kind-config.yaml

kind Cluster

Tells kind how to build the cluster. This is kind's own config format, not a Kubernetes object: it is read once by the kind CLI and never sent to the API server.

Used by kind create cluster --config (up.sh step 1)

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080
        hostPort: 8080
        protocol: TCP
FieldHereWhat it does
apiVersion / kindkind.x-k8s.io/v1alpha4 · ClusterIdentifies the kind config schema. kubectl would not understand this file.
nodes[].rolecontrol-planeOne node only. On a single-node cluster kind lets ordinary pods run on the control-plane node, so all Jobs, the dashboard and the PVC live on the same machine. Add - role: worker entries to get more nodes, but then the ReadWriteOnce PVC can only follow pods onto one of them.
extraPortMappings.containerPort30080A port on the node container. It has to equal the dashboard Service's nodePort in 50-dashboard.yaml.
extraPortMappings.hostPort8080Docker publishes it on your Mac. This is the only reason http://localhost:8080 works. Port mappings are fixed when the cluster is created; changing them means down.sh and up.sh again.

manifests/base/00-namespace.yaml

Namespace

Creates the builds namespace that every other object lives in.

Used by kubectl apply -k manifests/base

apiVersion: v1
kind: Namespace
metadata:
  name: builds
  labels:
    app.kubernetes.io/part-of: k8s-platform
FieldHereWhat it does
metadata.namebuildsNamespaced objects in the other files say namespace: builds. Names only need to be unique within one namespace.
metadata.namespace(none)A Namespace is itself cluster-scoped, so it has no namespace field.
metadata.labelsapp.kubernetes.io/part-of: k8s-platformOne of Kubernetes' recommended labels. The platform puts it on most objects so you can select everything at once, e.g. kubectl get jobs -l app.kubernetes.io/part-of=k8s-platform (what status.sh and the dashboard do).

Deleting the namespace deletes everything inside it, PVC included. That's a quick reset that keeps the cluster.

manifests/base/10-pvc.yaml

PersistentVolumeClaim

Asks for 2Gi of disk that outlives any pod. The clone Job writes sources here and the build Job reads them in another pod.

Used by kubectl apply -k manifests/base; mounted by every Job and the dashboard

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: workspace
  namespace: builds
  labels:
    app.kubernetes.io/part-of: k8s-platform
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 2Gi
FieldHereWhat it does
spec.accessModes["ReadWriteOnce"]RWO means the volume can be mounted read-write by pods on one node at a time. It does not mean one pod. With one kind node, all pods share it. On a multi-node cluster you'd need ReadWriteMany from an NFS/EFS-style StorageClass.
spec.resources.requests.storage2GiThe size asked for. The local-path provisioner kind uses does not enforce it (it's a plain directory), but cloud provisioners create a disk of this size.
spec.storageClassName(not set)Omitted on purpose, so the cluster's default StorageClass is used: standard on kind (local-path, waits for the first pod before creating the volume) and the hostpath provisioner on Minikube. The same file works on both.
metadata.nameworkspaceWhat pods refer to with persistentVolumeClaim.claimName: workspace. Pods never name the PV itself.

The PV is created for you (dynamic provisioning). See it with kubectl get pv. Deleting the PVC deletes the PV and its data on kind, because the StorageClass's reclaim policy is Delete.

manifests/base/20-rbac.yaml

ServiceAccount Role RoleBinding

Three objects in one file, separated by ---. Together they give pods running as build-agent the right to manage Jobs and ConfigMaps in builds, and nothing else.

Used by kubectl apply -k manifests/base; used by orchestrator, build-agent and dashboard pods

apiVersion: v1
kind: ServiceAccount
metadata:
  name: build-agent
  namespace: builds
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: build-agent
  namespace: builds
rules:
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["create", "get", "list", "watch", "delete"]
  - apiGroups: ["batch"]
    resources: ["cronjobs"]
    verbs: ["get", "list"]
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "create", "patch", "update"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: build-agent
  namespace: builds
subjects:
  - kind: ServiceAccount
    name: build-agent
    namespace: builds
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: build-agent
FieldHereWhat it does
ServiceAccount metadata.namebuild-agentAn identity for pods. Pods opt in with serviceAccountName: build-agent and get a token for it mounted automatically.
Role rules[].apiGroups"batch" / ""Which API group the resource belongs to. Jobs and CronJobs are in batch; pods and configmaps are in the core group, written as an empty string "". Find any resource's group with kubectl api-resources.
Role rules[].resourcesjobs, cronjobs, pods, pods/log, configmapsPlural resource names. pods/log is a subresource: reading logs needs its own permission on top of reading pods.
Role rules[].verbscreate, get, list, watch, delete, patch, updateWhat's allowed. Note what's absent: no delete on pods, no access to secrets. A Role is limited to its own namespace; a ClusterRole would be cluster-wide.
RoleBinding subjectsServiceAccount build-agent in buildsWho gets the rights. Could also be a User or Group.
RoleBinding roleRefRole build-agentWhich Role is granted. roleRef can't be changed after creation; to point at another Role you delete and recreate the binding.

manifests/base/30-config.yaml

ConfigMap ×2

Two ConfigMaps. platform-config holds settings; build-status starts empty and is used as a small database of build records.

Used by kubectl apply -k manifests/base; read via envFrom, patched by the agents

apiVersion: v1
kind: ConfigMap
metadata:
  name: platform-config
  namespace: builds
data:
  REPOS: "k8s-java8=https://github.com/tanmaypatil/k8s-java8.git,k8s-java17=https://github.com/tanmaypatil/k8s-java17.git"
  GIT_REF: "main"
  JAVA_8_IMAGE: "k8s-platform/java8-maven:dev"
  JAVA_17_IMAGE: "k8s-platform/java17-maven:dev"
  AGENT_IMAGE: "k8s-platform/agent:dev"
  GIT_IMAGE: "alpine/git:2.47.2"
  KEEP_RUNS: "10"
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: build-status
  namespace: builds
  labels:
    app.kubernetes.io/part-of: k8s-platform
data: {}
FieldHereWhat it does
platform-config data.REPOS"k8s-java8=…,k8s-java17=…"The repos to build, name=url comma-separated. Names become parts of Job names, so they must be lowercase DNS labels (the orchestrator checks).
data.JAVA_8_IMAGE / JAVA_17_IMAGEk8s-platform/java8-maven:dev …The build agent scans its environment for JAVA_<N>_IMAGE keys to know which JDKs exist. Adding JAVA_21_IMAGE is all it takes to support Java 21.
data.AGENT_IMAGE / GIT_IMAGEk8s-platform/agent:dev · alpine/git:2.47.2Images for the Jobs the agents create at run time. kustomize can't rewrite images hidden inside strings, which is why the registry overlay patches these keys.
data.KEEP_RUNS / GIT_REF"10" · "main"All ConfigMap values are strings, so numbers are quoted. envFrom turns every key into an environment variable.
build-status data{}Empty at creation; the agents add one key per <build-id>.<repo>. A ConfigMap is capped at about 1 MiB, which is one reason old runs are pruned.

Environment variables from envFrom are read when a container starts. Editing platform-config affects the next Job, never one that is already running.

manifests/base/40-orchestrator-cronjob.yaml

CronJob

A CronJob that never runs on a schedule. It stores the orchestrator's Job definition so trigger.sh and the dashboard can stamp out a copy on demand.

Used by kubectl apply -k manifests/base; copied by kubectl create job --from=cronjob/orchestrator

apiVersion: batch/v1
kind: CronJob
metadata:
  name: orchestrator
  namespace: builds
  labels:
    app.kubernetes.io/part-of: k8s-platform
spec:
  schedule: "0 0 1 1 *"
  suspend: true
  concurrencyPolicy: Forbid
  jobTemplate:
    metadata:
      labels:
        app.kubernetes.io/part-of: k8s-platform
        k8s-platform/stage: orchestrator
    spec:
      backoffLimit: 0
      ttlSecondsAfterFinished: 86400
      template:
        metadata:
          labels:
            app.kubernetes.io/part-of: k8s-platform
            k8s-platform/stage: orchestrator
        spec:
          serviceAccountName: build-agent
          restartPolicy: Never
          containers:
            - name: orchestrator
              image: k8s-platform/agent:dev
              imagePullPolicy: IfNotPresent
              command: ["python", "/app/agent/orchestrator.py"]
              env:
                - name: BUILD_ID   # downward API: the Job's own name
                  valueFrom:
                    fieldRef:
                      fieldPath: metadata.labels['batch.kubernetes.io/job-name']
              envFrom:
                - configMapRef:
                    name: platform-config
              volumeMounts:
                - name: workspace
                  mountPath: /workspace
              resources:
                requests: {cpu: 50m, memory: 64Mi}
                limits: {memory: 256Mi}
          volumes:
            - name: workspace
              persistentVolumeClaim:
                claimName: workspace
FieldHereWhat it does
spec.schedule"0 0 1 1 *"Required by the schema, so it holds a placeholder (midnight on 1 January). It never fires because of suspend.
spec.suspendtrueStops the CronJob controller from creating Jobs on schedule. Manual create job --from still works.
spec.concurrencyPolicyForbidOnly applies to runs the schedule would start. It does not stop two manual triggers from running at once.
jobTemplate.spec.backoffLimit0The orchestrator is not retried: a second attempt would create duplicate clone Jobs.
jobTemplate.spec.ttlSecondsAfterFinished86400Kubernetes deletes the finished orchestrator Job (and its pod and logs) after 24 hours.
template.spec.serviceAccountNamebuild-agentThe orchestrator creates Jobs and patches build-status, so it needs the RBAC identity.
template.spec.restartPolicyNeverJobs only allow Never or OnFailure. With Never, a crash fails the pod instead of restarting it in place.
containers[].imagePullPolicyIfNotPresentUse the image already on the node (loaded by kind load) and don't contact a registry.
env BUILD_ID valueFrom.fieldRefmetadata.labels['batch.kubernetes.io/job-name']The downward API: the pod reads its own label, which the Job controller sets to the Job's name. So the Job name run-20261101-140500 becomes the build id.
envFrom.configMapRefplatform-configEvery key of the ConfigMap becomes an environment variable.
resourcesrequests cpu 50m, memory 64Mi · limits memory 256MiRequests are what the scheduler reserves; the memory limit is where the container gets OOM-killed. No CPU limit, so it's never throttled.
volumes[].persistentVolumeClaim.claimNameworkspaceMounted at /workspace so the orchestrator can prune old runs' folders.

manifests/base/50-dashboard.yaml

Deployment Service

The only long-running app. The Deployment keeps one pod alive; the Service gives it a stable address and a port on the node.

Used by kubectl apply -k manifests/base

apiVersion: apps/v1
kind: Deployment
metadata:
  name: dashboard
  namespace: builds
  labels:
    app.kubernetes.io/part-of: k8s-platform
    app: dashboard
spec:
  replicas: 1
  selector:
    matchLabels:
      app: dashboard
  template:
    metadata:
      labels:
        app: dashboard
    spec:
      serviceAccountName: build-agent
      containers:
        - name: dashboard
          image: k8s-platform/agent:dev
          imagePullPolicy: IfNotPresent
          command: ["python", "/app/dashboard/server.py"]
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: platform-config
          readinessProbe:
            httpGet: {path: /healthz, port: 8080}
            periodSeconds: 5
          volumeMounts:
            - name: workspace
              mountPath: /workspace
              readOnly: true
          resources:
            requests: {cpu: 50m, memory: 64Mi}
            limits: {memory: 256Mi}
      volumes:
        - name: workspace
          persistentVolumeClaim:
            claimName: workspace
---
apiVersion: v1
kind: Service
metadata:
  name: dashboard
  namespace: builds
spec:
  type: NodePort
  selector:
    app: dashboard
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
FieldHereWhat it does
Deployment spec.replicas1How many identical pods to keep running. If the pod dies, a new one is created.
spec.selector.matchLabelsapp: dashboardHow the Deployment finds its pods. It must match template.metadata.labels, and it can't be changed after creation.
template.spec.serviceAccountNamebuild-agentThe dashboard lists Jobs, reads build-status, and its Run button creates Jobs.
ports[].containerPort8080Documents the port server.py listens on. Informational; the Service's targetPort is what routes traffic.
readinessProbe.httpGet/healthz on 8080, every 5sUntil this returns 200 the pod isn't "Ready": the Service won't send it traffic and rollout status keeps waiting. There's no livenessProbe, so a hung server isn't restarted automatically.
volumeMounts[].readOnlytrueThe dashboard only reads build logs from the PVC and can't damage them.
Service spec.typeNodePortOpens a port on every node. ClusterIP (the default) would be reachable only inside the cluster.
Service spec.selectorapp: dashboardSends traffic to Ready pods carrying this label: the same label the Deployment puts on its pods.
port / targetPort / nodePort80 / 8080 / 30080Three numbers: port is the Service's port inside the cluster (http://dashboard.builds), targetPort is the container's port, nodePort (30000-32767) is on the node and is what kind maps to localhost:8080.

resources00-namespace.yaml … 50-dashboard.yamlThe files to include. The number prefixes keep the list tidy, but kustomize sorts output by kind anyway (Namespace, ServiceAccount, Role, RoleBinding, ConfigMap, Service, PVC, Deployment, CronJob).

manifests/templates/clone-job.yaml

Job (template)

Shallow-clones one repo onto the PVC. Not valid YAML for Kubernetes as-is: Python's string.Template fills the ${…} placeholders first.

Used by the orchestrator, per repo per run (kube.create_job)

apiVersion: batch/v1
kind: Job
metadata:
  name: ${JOB_NAME}
  labels:
    app.kubernetes.io/part-of: k8s-platform
    k8s-platform/stage: clone
    k8s-platform/build-id: ${BUILD_ID}
    k8s-platform/repo: ${REPO}
spec:
  backoffLimit: 2                # retry flaky network clones
  activeDeadlineSeconds: 300
  ttlSecondsAfterFinished: 3600  # Kubernetes deletes the Job an hour after it ends
  template:
    metadata:
      labels:
        app.kubernetes.io/part-of: k8s-platform
        k8s-platform/stage: clone
        k8s-platform/build-id: ${BUILD_ID}
        k8s-platform/repo: ${REPO}
    spec:
      restartPolicy: Never
      automountServiceAccountToken: false   # never calls the Kubernetes API, so no token
      containers:
        - name: git
          image: ${GIT_IMAGE}
          imagePullPolicy: IfNotPresent
          env:
            - name: REPO_URL
              value: "${REPO_URL}"
            - name: GIT_REF
              value: "${GIT_REF}"
            - name: DEST
              value: /workspace/runs/${BUILD_ID}/${REPO}
          envFrom:
            - configMapRef: {name: build-env, optional: true}   # e.g. proxy settings
          command: ["/bin/sh", "-c"]
          args:
            - >-
              rm -rf $(DEST) && mkdir -p $(DEST) &&
              git clone --depth 1 --branch $(GIT_REF) $(REPO_URL) $(DEST) &&
              git -C $(DEST) log -1 --format='cloned %h %s'
          volumeMounts:
            - {name: workspace, mountPath: /workspace}
            - {name: extra-ca, mountPath: /etc/extra-ca, readOnly: true}
          resources:
            requests: {cpu: 100m, memory: 64Mi}
            limits: {memory: 256Mi}
      volumes:
        - name: workspace
          persistentVolumeClaim: {claimName: workspace}
        - name: extra-ca
          configMap: {name: extra-ca, optional: true}
FieldHereWhat it does
metadata.name${JOB_NAME}e.g. clone-k8s-java8-run-20261101-140500. Object names are capped at 63 characters here (the code truncates).
labels (on Job and pod template)stage, build-id, repoRepeated on the pod template so pods can be selected too. kubectl get jobs -l k8s-platform/stage=clone finds every clone.
spec.backoffLimit2Up to two retries in new pods, for network hiccups.
spec.activeDeadlineSeconds300A hard cap for the whole Job, retries included. After 5 minutes the Job fails with DeadlineExceeded.
spec.ttlSecondsAfterFinished3600Auto-delete the Job and its pods an hour after it ends.
automountServiceAccountTokenfalsegit never calls the Kubernetes API, so the pod gets no credentials.
env DEST + args $(DEST)/workspace/runs/${BUILD_ID}/${REPO}Two kinds of placeholder: ${…} is filled by Python before submitting; $(DEST) is expanded by Kubernetes from the container's own env vars when it starts.
command / args["/bin/sh","-c"] + scriptcommand replaces the image's entrypoint, args its arguments. >- folds the YAML lines into one shell command.
envFrom … optional: truebuild-envLoad proxy settings if a build-env ConfigMap exists; if not, the pod still starts.
volumes extra-ca configMap optionalextra-caMounts a ConfigMap as files (here a CA certificate), optional for the same reason.

manifests/templates/build-agent-job.yaml

Job (template)

Runs build_agent.py, which reads pom.xml, chooses a JDK image and creates the build Job.

Used by the orchestrator, after the clone Job completes

apiVersion: batch/v1
kind: Job
metadata:
  name: ${JOB_NAME}
  labels:
    app.kubernetes.io/part-of: k8s-platform
    k8s-platform/stage: build-agent
    k8s-platform/build-id: ${BUILD_ID}
    k8s-platform/repo: ${REPO}
spec:
  backoffLimit: 0
  activeDeadlineSeconds: 1200
  ttlSecondsAfterFinished: 3600
  template:
    metadata:
      labels:
        app.kubernetes.io/part-of: k8s-platform
        k8s-platform/stage: build-agent
        k8s-platform/build-id: ${BUILD_ID}
        k8s-platform/repo: ${REPO}
    spec:
      serviceAccountName: build-agent
      restartPolicy: Never
      containers:
        - name: build-agent
          image: ${AGENT_IMAGE}
          imagePullPolicy: IfNotPresent
          command: ["python", "/app/agent/build_agent.py"]
          env:
            - {name: BUILD_ID, value: "${BUILD_ID}"}
            - {name: REPO, value: "${REPO}"}
          envFrom:
            - configMapRef: {name: platform-config}
          volumeMounts:
            - {name: workspace, mountPath: /workspace}
          resources:
            requests: {cpu: 50m, memory: 64Mi}
            limits: {memory: 256Mi}
      volumes:
        - name: workspace
          persistentVolumeClaim: {claimName: workspace}
FieldHereWhat it does
serviceAccountNamebuild-agentUnlike clone and build, this pod talks to the API (creates a Job, patches status), so it uses the RBAC identity and keeps its token.
spec.backoffLimit0A retry would try to create a build Job that already exists.
spec.activeDeadlineSeconds1200Longer than the build Job's 900s, so the agent outlives the build it is waiting on and can record the result.
env BUILD_ID / REPOvalue: "${BUILD_ID}"Plain values filled in by the orchestrator: which run and which repo this agent handles.
envFrom platform-configBrings in every JAVA_<N>_IMAGE the agent picks from.
image${AGENT_IMAGE}The same agent image as the orchestrator and dashboard, running a different script.

manifests/templates/build-job.yaml

Job (template)

Runs mvn package in the matching JDK image against the sources on the PVC. This is the Job that does the real work.

Used by the build agent, with the image it chose

apiVersion: batch/v1
kind: Job
metadata:
  name: ${JOB_NAME}
  labels:
    app.kubernetes.io/part-of: k8s-platform
    k8s-platform/stage: build
    k8s-platform/build-id: ${BUILD_ID}
    k8s-platform/repo: ${REPO}
    k8s-platform/java: "${JAVA_VERSION}"
spec:
  backoffLimit: 0                # a failed compile should not be retried
  activeDeadlineSeconds: 900
  ttlSecondsAfterFinished: 3600
  template:
    metadata:
      labels:
        app.kubernetes.io/part-of: k8s-platform
        k8s-platform/stage: build
        k8s-platform/build-id: ${BUILD_ID}
        k8s-platform/repo: ${REPO}
        k8s-platform/java: "${JAVA_VERSION}"
    spec:
      restartPolicy: Never
      automountServiceAccountToken: false   # never calls the Kubernetes API, so no token
      containers:
        - name: maven
          image: ${BUILD_IMAGE}
          imagePullPolicy: IfNotPresent
          command: ["run-build"]
          env:
            - {name: SRC_DIR, value: /workspace/runs/${BUILD_ID}/${REPO}}
            - {name: LOG_FILE, value: /workspace/logs/${BUILD_ID}/${REPO}.log}
            - {name: ARTIFACT_DIR, value: /workspace/artifacts/${BUILD_ID}/${REPO}}
            - {name: MAVEN_REPO, value: /workspace/m2}
            - {name: MAVEN_GOALS, value: package}
          envFrom:
            - configMapRef: {name: build-env, optional: true}   # e.g. proxy settings
          volumeMounts:
            - {name: workspace, mountPath: /workspace}
            - {name: extra-ca, mountPath: /etc/extra-ca, readOnly: true}
          resources:
            requests: {cpu: 500m, memory: 512Mi}
            limits: {memory: 1Gi}
      volumes:
        - name: workspace
          persistentVolumeClaim: {claimName: workspace}
        - name: extra-ca
          configMap: {name: extra-ca, optional: true}
FieldHereWhat it does
labels k8s-platform/java"${JAVA_VERSION}"Quoted because label values must be strings. Unquoted 17 is a YAML number and the API server would reject it.
spec.backoffLimit0A compile error won't fix itself, so fail on the first attempt.
spec.activeDeadlineSeconds900Kill a build that hangs after 15 minutes.
automountServiceAccountTokenfalseMaven runs downloaded plugins; the pod gets no Kubernetes credentials it could leak.
image${BUILD_IMAGE}k8s-platform/java8-maven:dev or java17-maven:dev: the decision the build agent made.
command["run-build"]The script baked into both build images (images/build-scripts/run-build.sh).
env SRC_DIR / LOG_FILE / ARTIFACT_DIR / MAVEN_REPO/workspace/…Where to read sources, write the log, put the jar, and keep the Maven cache. All paths on the shared PVC.
resourcesrequests cpu 500m, memory 512Mi · limits memory 1GiThe biggest requests in the platform. If the node can't fit them, the pod stays Pending. Maven above 1Gi is OOM-killed (exit 137).

manifests/overlays/registry/kustomization.yaml

Kustomization

Reuses the whole base and changes only what differs when images come from a registry. This is kustomize's base/overlay pattern.

Used by up.sh when REGISTRY is set: kubectl kustomize … | sed … | kubectl apply -f -

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
  - default-serviceaccount.yaml
images:

Patterns that repeat across files

The three Job timers

JobbackoffLimitactiveDeadlineSecondsttlSecondsAfterFinishedWhy
orchestrator (CronJob template)0none86400 (24h)A retry would duplicate the whole run; keep it a day for its logs.
clone23003600Network failures are often transient.
build-agent012003600Must outlive the build it waits on.
build09003600Compile errors are deterministic.

backoffLimit is how many times a failed pod is replaced. activeDeadlineSeconds caps the Job's total running time, across retries. ttlSecondsAfterFinished is garbage collection: after that long, Kubernetes deletes the finished Job and its pods.

Requests and limits

Every container sets a CPU and memory request (what the scheduler reserves) and a memory limit (past it, the container is OOM-killed with exit code 137). None sets a CPU limit, so a container can use spare CPU instead of being throttled. If requests add up to more than the node has, new pods wait in Pending.

Optional references

configMapRef: {name: build-env, optional: true} and configMap: {name: extra-ca, optional: true} let one template work on a home network and behind a corporate proxy. Without optional, a missing ConfigMap keeps the pod stuck in CreateContainerConfigError.

Labels as the query language

Every object carries app.kubernetes.io/part-of: k8s-platform, and every Job adds k8s-platform/stage, /build-id, /repo (and /java for builds). The dashboard and status.sh use these instead of parsing names:

kubectl -n builds get jobs -l k8s-platform/stage=build -L k8s-platform/repo,k8s-platform/java
kubectl -n builds get pods -l k8s-platform/build-id=run-20261101-140500
